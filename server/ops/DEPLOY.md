# StudyHub 1.3.3-dev — эксплуатационный регламент

Это подготовка к пилотному развёртыванию, не действующий VPS. Не объединять с main. СУБД MySQL 8.4 LTS, FastAPI, Nginx на хосте. Старая PWA продолжает работать через Pages. До запуска с реальными MAX ID проверить правовое основание обработки, уведомление об обработке данных, сроки хранения и локализацию в РФ; не публиковать дампы, токены, MAX ID и `.env`.

## 1. Подготовка VPS

Рекомендуется российский Linux VPS (2 vCPU, 4 GB RAM, 40–60 GB SSD как стартовая оценка), отдельный домен, SSH-ключ, firewall с разрешением только необходимого SSH, 80/443. Установить Docker Engine + Compose v2, Nginx, Certbot, Git, gzip, GNU coreutils. Проверить `docker compose version`, синхронизацию часов, DNS A/AAAA (если IPv6 не используется, не публиковать AAAA). Членство в docker-группе фактически даёт root-полномочия. Использовать доверенного оператора. Развёртывать из проверенного коммита, не запускать автоматически непроверенный develop на VPS.

В примерах репозиторий расположен в `/opt/studyhub`, рабочий каталог `/opt/studyhub/server`. При другом пути изменить systemd unit-файлы. В первый раз:

```bash
cd /opt/studyhub/server
umask 077
cp .env.example .env
chmod 600 .env
# В локальном редакторе задать разные длинные случайные MYSQL_ROOT_PASSWORD и MYSQL_PASSWORD.
# MAX_BOT_TOKEN оставить пустым. Не использовать CI-пароли.
docker compose config --quiet
docker compose up -d db --wait
docker compose build api
docker compose run --rm api alembic upgrade head
# Перед первым импортом сверить свежие data.json/content.json в main.
# При необходимости заменить локальные seed/data.json и seed/content.json и пересобрать api.
docker compose run --rm api python -m app.import_data
docker compose up -d api --wait
curl -fsS http://127.0.0.1:8000/health
```

Порт MySQL не опубликован; API доступен только на loopback хоста. Не открывать 3306/8000 в firewall. API-контейнер non-root, с read-only root filesystem, tmpfs, no-new-privileges, без capabilities. Команда healthcheck проверяет подключение к БД. Статус unhealthy виден в `docker compose ps`; Compose сам по себе не перезапускает контейнер только из-за unhealthy. Мониторинг: `curl -fsS https://ДОМЕН/health`, `docker compose ps`, `journalctl -u studyhub-maintenance.service -u studyhub-backup.service`. Отдельные внешние алерты не подключены.

## 2. HTTPS

Сначала получить сертификат на реальный домен (например, Certbot standalone на свободном порту 80, временно остановив конфликтующий веб-сервер). Затем скопировать `ops/nginx.conf.example` в `/etc/nginx/conf.d/studyhub.conf`, заменить ВСЕ `studyhub.example.invalid` на согласованный домен и проверить реальные пути ключа/цепочки сертификата. Не использовать примерный домен или тестовый сертификат в production. Если IPv6 отключён, убрать listen [::].

```bash
sudo nginx -t
sudo systemctl enable --now nginx
sudo systemctl reload nginx
```

Проверить HTTPS извне, HTTP→HTTPS, `/cabinet/`, `/health`, отсутствие доступа к 3306/8000; проверить автоматическое продление сертификата и reload Nginx после него. Конфигурация ограничивает размер тела и частоту запросов, закрывает публичные `/docs`, `/redoc`, `/openapi.json`; access logs отключены. Лимиты на IP требуют настройки при большом числе студентов за одним NAT. Не включать агрессивную CSP/frame-ancestors без проверки MAX WebView. Проверить настоящий вход MAX отдельно.

## 3. Операторское управление доступом

Только после получения достоверного MAX ID пользователя (не номер телефона и не номер зачётки). Внутри server:

```bash
docker compose exec -T api python -m app.access_cli list
# ID ниже заменяется на проверенный числовой идентификатор.
docker compose exec -T api python -m app.access_cli grant VERIFIED_ID student --group knitu-661-m52-2026-1
docker compose exec -T api python -m app.access_cli grant VERIFIED_ID admin --group knitu-661-m52-2026-1
docker compose exec -T api python -m app.access_cli grant VERIFIED_ID owner --group knitu-661-m52-2026-1
docker compose exec -T api python -m app.access_cli revoke-owner VERIFIED_ID
docker compose exec -T api python -m app.access_cli disable VERIFIED_ID
```

`grant student` снимает роль админа только в указанной группе, но не глобальный owner. `revoke-owner` снимает глобальную роль, оставляя прежние роли в группах; при необходимости отдельно заменить admin на student. Не отзывать доступ единственного владельца без плана восстановления. `disable` отключает учётную запись целиком, не удаляет прогресс. CLI выводит MAX ID — не пересылать его вывод и не публиковать логи. Саморегистрация, приглашения и полноценное управление новыми группами через веб пока не реализованы. Операции CLI не входят в административный HTTP-аудит: вести операторский журнал отдельно. Подключать реальный MAX_BOT_TOKEN в `.env` только после проверки HTTPS и верификации бота; пересоздать api, проверить разрешённого студента/админа, отказ незарегистрированному пользователю, выход, повторный вход. Настоящие токены не вводить в CI.

## 4. Синхронизация и обслуживание

`docker compose exec -T api python -m app.maintenance all` сначала удаляет просроченные сессии, затем загружает только доверенный публичный JSON StudyHub с фиксированного HTTPS URL. Переадресации запрещены, размер ограничен. При ошибке, устаревшей или неполной проверке сохраняется предыдущий снимок. Задания, объявления, прогресс и роли не перезаписываются. Проверка источника осуществляется GitHub Actions 1.2; сервер считывает опубликованный результат каждые 30 минут. При возрасте проверки более 12 ч кабинет показывает предупреждение. После 24.01.2027 требуется отдельная настройка охвата нового семестра, нельзя автоматически объявлять отсутствие занятий. Успешная синхронизация повторно загружает те же записи; оптимизация повторов возможна позднее.

```bash
sudo cp ops/studyhub-maintenance.{service,timer} /etc/systemd/system/
sudo cp ops/studyhub-backup.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now studyhub-maintenance.timer studyhub-backup.timer
sudo systemctl start studyhub-maintenance.service
sudo systemctl start studyhub-backup.service
systemctl list-timers 'studyhub-*'
```

Синхронизация: 00/30 минут каждого часа + случайная задержка до минуты. Резервное копирование: 03:30 МСК каждый день. Таймеры требуют работающего VPS и systemd. Это локальные таймеры, а не новые автоматизации ChatGPT. Наблюдать `journalctl`, проверять ошибки. Не подключать одновременно другой процесс импорта полного JSON после административных изменений.

## 5. Backup / Restore

Резервная копия — согласованный InnoDB dump (`--single-transaction`, без блокировки таблиц; не выполнять миграции/DDL во время создания), gzip, SHA256, каталог 0700, файлы 0600. Не переиспользовать каталог другого назначения. Не хранить на публичных ресурсах; дамп содержит персональные данные и хэши сессий. Скрипт не удаляет старые копии автоматически; согласовать срок хранения и контролировать место. Контрольная сумма обнаруживает случайное повреждение, не является криптографической подписью. Копии на том же VPS не защищают от его потери: перед production настроить отдельное зашифрованное российское хранилище с доступом оператора, проверить его восстановление. Не отправлять дампы в GitHub Actions artifacts.

```bash
sudo bash ops/backup.sh /var/lib/studyhub-backups
sudo bash ops/verify-backup.sh /var/lib/studyhub-backups/ИМЯ_КОПИИ
```

Проверка восстановления выполняется только в изолированном тестовом проекте Compose с **новым томом**, новым `.env`, другим портом API или без запуска API. Проверить, что имя проекта и том не совпадают с production; не запускать API на восстановленных данных с реальным MAX токеном. Скопировать проверенный dump в защищённый каталог, подготовить новый пустой MySQL с тем же именем БД, восстановить через `gzip -dc /path/database.sql.gz | docker compose -p studyhub-restore exec -T db sh -c 'export MYSQL_PWD="$MYSQL_ROOT_PASSWORD"; mysql -uroot "$MYSQL_DATABASE"'` из отдельного каталога. Не выполнять этот конвейер в действующем проекте. Команда должна выполняться с `set -o pipefail`. Сверить Alembic revision, количество записей и выборочные данные, FK и API на тестовых данных. Для аварийного возврата в production остановить запись, сохранить текущее состояние отдельно, переключить на проверенный восстановленный том по отдельному согласованному регламенту. При восстановлении старого снимка отозвать все ранее выданные сессии (DELETE FROM auth_sessions) до возобновления API; проверить риск повторного использования launch-данных (не принимать старые launch, выдержать 5 мин при отключённой авторизации). Не удалять оригинальный том до подтверждения. Не использовать `docker compose down -v` на рабочей системе.

CI репетирует backup/restore на синтетической базе: отдельная `studyhub_restore_ci` в одноразовом контейнере; проверяются 38 заданий, 49 событий, 40 тем, объявление, тестовый пользователь, членство, прогресс, аудит и ревизия. CI не содержит настоящих пользовательских данных.

## 6. Обновление

До смены кода: убедиться в успехе постоянного CI, сделать проверенную резервную копию, зафиксировать коммит, остановить запись при миграции, пересобрать API, применить Alembic, запустить, проверить HTTPS и /health. Для 1.3.3 новых таблиц нет. Не запускать повторный полный импорт на рабочей базе с административными изменениями. При ошибке не откатывать БД автоматически, сначала определить совместимость и согласовать восстановление.

## 7. Что остаётся до боевого запуска

Сервер/домен/сертификат, внешний мониторинг с оповещениями, off-site backup, проверка полного восстановления на VPS, согласование обработки персональных данных, реальная интеграция MAX и эксплуатационные проверки с настоящим аккаунтом. Полноценная регистрация и управление группами через веб не входят в этот пакет. Браузерный вход вне MAX также не реализован.
